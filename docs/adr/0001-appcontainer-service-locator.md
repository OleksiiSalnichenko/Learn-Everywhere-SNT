# 0001. AppContainer як сервіс-локатор замість Hilt/Dagger

## Контекст

Застосунок однопроцесний, без бекенду, з п'ятьма функціональними межами
(data, translation, voice, playback, settings) і UI-шаром зверху. Бриф прямо
просив не ускладнювати конструкціями (п.8).

## Рішення

Залежності збираються вручну одним класом `AppContainer` (сервіс-локатор,
без Hilt/Dagger). Кожен модуль виставляє вузький публічний інтерфейс
(`DictionaryRepository`, `TranslationService`, `SpeechInput`/`LanguageDetector`/
`Speaker`, `PlaybackController`, `SettingsRepository`) і ховає деталі
реалізації (схему бази, HTTP-парсинг, доступ до `SpeechRecognizer`/
`TextToSpeech`, конечний автомат програвання, ключі DataStore).

## Чому

Розглядали Hilt/Dagger — стандарт для Android DI. Відкинули: генерація коду
й анотації складніше пояснити в коментарях, ніж прямий виклик конструктора,
а розмір застосунку (п'ять модулів, один процес) не виправдовує вартість
навчання й налагодження DI-фреймворка. `AppContainer` — найпростіший спосіб
зв'язати сервіси, який усе ж лишає чіткі публічні межі для тестів: ті самі
інтерфейси служать швами для юніт-тестів, найважливіший — `PlaybackController`.

## Наслідки

Об'єкти створюються вручну в `AppContainer` — при рості кількості сервісів
клас розростається, а зв'язки між ними стають неявними: немає перевірки
графа залежностей на етапі компіляції, як у Dagger. Життєвий цикл
(singleton на застосунок) — відповідальність розробника, не фреймворка.
Перехід на Hilt пізніше означає переписати ініціалізацію застосунку і,
ймовірно, конструктори більшості класів.
