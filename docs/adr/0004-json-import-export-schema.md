# 0004. JSON-схема імпорту/експорту з мовою, яку задає користувач

## Контекст

Словник має експортуватись у файл і імпортуватись назад, потенційно на
іншому пристрої чи в іншій інсталяції застосунку.

## Рішення

Схема JSON фіксована:
`{"dictionaryName", "language", "words": [{"ukrainian","translation1","translation2","example"}]}`.
Мову словника при імпорті обирає користувач, а не значення `language` з
файлу автоматично. Некоректна структура файлу — явна помилка, імпорт
виконується все-або-нічого (без часткового наповнення словника).

## Чому

Розглядали автоматичне визначення мови зі значення `language` у файлі —
відкинули: файл можна відредагувати вручну або отримати з іншого джерела,
сліпа довіра до цього поля обійшла б явний вибір словника-мети й могла б
мовчки покласти слова не в ту вкладку. Явний вибір мови користувачем під час
імпорту коштує один зайвий клік, зате не приховує помилку. Часткового
імпорту при кривому файлі свідомо немає: часткова заливка залишила б
словник у невизначеному стані, який довелося б чистити вручну.

## Наслідки

Формат — публічний контракт: щойно користувачі почнуть обмінюватися
експортованими файлами, зміна полів (перейменування, нова обов'язкова
властивість) ламає сумісність зі старими файлами — версійного поля в схемі
зараз немає. `translation2` і `example` зафіксовані саме в цій формі; якщо
кількість перекладів на слово колись зросте (див. ADR 0002), доведеться
міняти і схему файлу, і код парсера з урахуванням уже існуючих експортів.
